# go-agent-claw 生产级能力开发计划

制定日期：2026-09-23；调整日期：2026-09-28。基于初始 main 分支的代码分析，按里程碑推进；当前完成情况见任务勾选和验收记录。勾选状态只表示本计划的验收记录，不代替代码核验。

## 目标与范围

先交付可控、可恢复、可验收的单机 Agent，再建设多用户服务。首个目标场景是开发者在指定项目中完成代码阅读、修改和验证；飞书作为后续服务入口。

生产级的判定依据是：权限有边界、执行有预算、失败可解释、中断可恢复、完成有证据、变更有回归验证。

按一名熟悉 Go 的开发者全职投入规划，包含实现、测试与文档。原先的 37–57 个工作日是未经原型验证的粗估，不能作为总交付排期。阶段 1 拆成三个可验收里程碑；阶段 2、3 先验证隔离与恢复方案，再重估实现工期；阶段 4–6 的区间仅供容量规划，进入该阶段前重新估算。真实模型评测另需明确预算。

## 阶段 1：可控执行与正确反馈

目标：每次任务都有确定的运行状态、终止原因和资源上限。

### 开发任务

- [x] S1-01：建立 Mock Provider、假工具和临时工作区测试夹具，覆盖无工具回答、工具失败、多工具回写及取消；不依赖外部密钥。
- [x] S1-02：主循环将 RecoveryManager 的 `finalOutput` 写入 Observation；BashTool、SubagentTool 正确返回失败；Registry 在错误路径同时保留输出与错误原因；ReminderInjector 检查同轮全部工具结果。
- [x] S1-03：引入轻量 Run 对象和 RunOptions，先记录 RunID、SessionID、状态、起止时间与终止原因；单任务 CLI 根据运行结果返回退出码，REPL 保留会话并报告失败。Engine 仍负责循环编排。
- [x] S1-04：加入 MaxTurns 和总超时，主循环在发起下一次模型请求前检查硬性退出条件；正常结束、取消、轮数耗尽和超时有不同终止原因。
- [x] S1-05：贯通取消，Shell 管理进程组并回收后代进程；工具输出使用有界缓冲，文件读取使用有界读取。超时和截断通过结构化字段表达。
- [x] S1-06：同一 Session 从接收任务、追加用户消息到 Run 完成整体串行；飞书入口必须在追加消息前进入该串行边界，不能只锁住 Run。工具设置超时与并发上限；独立只读工具可限流并发，写工具和通用 Shell 暂按顺序执行。账单读取改为加锁快照。
- [x] S1-07：按 [M3 开发 spec](specs/m3-config-budget-trace.md) 统一 CLI/环境配置和入口选项传递；支持 Provider、模型、地址、Thinking、PlanMode 与运行预算，PlanMode 默认关闭。
- [x] S1-08：使用按 Provider/网关和模型匹配的不可变价格快照，费用记录包含币种、版本和“未知”状态；Trace 按 RunID 唯一导出且错误可见，清理原始敏感属性；同步 README 与 AGENTS.md。
- [x] S1-09：加入每 Run 的 Token 预算、每请求输出上限和主子任务共享账本；请求前原子预留、请求后按实际 Usage 结算。费用未知时不能按零费用放行费用预算，预算耗尽有确定的终止原因。

主要改动：`internal/engine`、`internal/tools`、`internal/context/session.go`、`internal/observability`、`internal/provider`、`cmd/claw`；按需新增 `internal/run`、`internal/config`。

### 验收门槛

- 里程碑 M1（参考 3–5 日）：S1-01 至 S1-04 完成，按 [M1 开发 spec](specs/m1-controlled-run.md) 验收。Mock Provider 的正常工具任务有 RunID 与正确结束原因；无限请求工具的任务在 MaxTurns 或总超时处停止，不能再发起模型请求。M1 的总超时依赖 Provider 和工具响应 context；Shell 后代进程回收属于 M2。
- 里程碑 M2（参考 4–7 日）：S1-05、S1-06 完成，按 [M2 开发 spec](specs/m2-cancellation-scheduling.md) 验收。取消、进程回收、输出上限和整轮 Session 串行通过测试；含飞书入口“追加消息 → Run”的并发测试。
- 里程碑 M3（参考 6–9 日）：S1-07 至 S1-09 按 [M3 开发 spec](specs/m3-config-budget-trace.md) 完成。CLI 配置、Token/费用预算、成本状态和 Trace 可验收；明确请求估算与实际账单差异后，才宣称阶段 1 的本地资源准入上限。
- Mock Provider 持续请求工具时，达到配置的 N 轮后不再发起新一轮模型请求。
- 失败的 Shell 保留 stderr，标记 IsError，恢复建议实际出现在下一次 Provider 输入中。
- 本地可控测试中，取消后 2 秒内释放工具、进程和等待协程；网络请求遵守已配置截止时间。
- 大输出不会导致缓冲无限增长；超时后无遗留测试子进程。
- 同一 Session 并发提交不会交叉追加或执行，飞书消息顺序可核对；主子任务并发时不能重复花费同一份预算余额。
- 预算控制明确区分预估与供应商最终账单，不承诺供应商侧绝对费用上限。
- 构建、静态检查和相关 race 测试通过。

S1-05、S1-06 已按 [M2 开发 spec](specs/m2-cancellation-scheduling.md) 实现。自动化测试覆盖同会话 FIFO、飞书提交顺序、排队取消、只读限流与写入屏障、工具元数据、输出上限、路径越界、Shell 进程组回收和审批取消。构建、vet、全量单元测试及相关 race 测试通过；并发关键包 `-race -count=10` 通过。Linux 仅完成交叉编译，目标平台运行验收与真实飞书事件/API 验证留待具备环境后执行；未运行付费 LLM 调用。

## 阶段 2：权限与执行隔离

目标：工具实际能做什么，由运行时权限决定。

隔离原型先在当前可用的 macOS Docker Desktop Linux VM 内验证，按 [阶段 2 开发 spec](specs/stage2-permissions-isolation.md) 实施本地后端；目标原生 Linux 主机验证保留为阶段最终平台验收门槛。原型和实现均不以宿主 Shell 作为自动回退。实际人日尚无可信记录，本地验收不用于承诺跨平台排期。

### 开发任务

- [x] S2-01：定义只读、工作区写入、进程执行、网络访问等能力；工具声明所需权限，Registry 在执行前统一检查。
- [x] S2-02：统一文件访问边界，覆盖相对路径穿越、绝对路径输入、符号链接和链接替换竞争；采用根目录约束的文件操作，避免只做字符串前缀检查。
- [x] S2-03：新增受限目录浏览与文本搜索工具；只读子智能体不挂载通用 BashTool，工具结果遵守输出上限。
- [x] S2-04：定义 Executor 接口，首个隔离后端选择 Linux 容器；macOS 开发通过容器运行时验证。使用非特权用户、受限挂载、CPU/内存/进程配额和显式网络策略，不挂载宿主容器控制接口。
- [x] S2-05：Shell 环境变量采用允许列表，不继承 Provider 密钥；隔离后端不可用时明确失败，不自动回退到宿主机执行。
- [x] S2-06：建立审批接口，授权绑定 Run、工具参数摘要、审批主体和期限；拒绝、过期和取消均有确定结果。先实现本地交互适配，非交互运行无审批来源时返回待处理或拒绝状态。
- [x] S2-07：区分用户指令与文件、工具结果中的外部文本；即使模型受到外部文本诱导，执行层仍独立验证权限。

主要改动：`internal/tools`、`internal/engine`、子智能体装配；新增 `internal/policy` 和 `internal/executor`。本地实现与验收已记录在 spec；目标 Linux 主机运行验收待执行。

### 验收门槛

- 越界读写、符号链接跳转和只读子任务写入用例全部被拒绝。
- 隔离进程不能读取宿主测试秘密、工作区外测试文件或访问被禁用的网络。
- 更改审批后的参数、过期审批和无授权主体均不能放行操作。
- 在测试文件中放置要求越权的指令，工具执行层仍拒绝越权调用。
- 资源耗尽、取消和隔离后端故障不会转入无限制执行。

### 实施记录（2026-10-03）

S2-01 至 S2-07 的本地实现已完成。权限检查、根目录约束与原子写入、受限浏览/搜索、只读子任务、Docker Executor、本地逐次审批和外部数据来源标记均已接入。CLI 综合回归覆盖 M1–M3 的工具回传、预算拒绝、多 Run、权限拒绝和无审批拒绝。Docker Desktop 验证了非 root、默认网络禁用、配额、实际 OOM、宿主测试秘密不可见、有界输出与取消后的容器回收。全量单测、race、vet、正式包构建及 Linux amd64 交叉构建通过；未调用真实 LLM 或飞书 API。

- [ ] 在目标原生 Linux 主机运行相同容器验收，确认 daemon/cgroup/文件权限行为。交叉构建不代替运行验收。
- [ ] 飞书可信主体审批在后续服务治理阶段实现；当前入口默认只读，旧审批卡片不授权新权限层。

## 阶段 3：持久化与故障恢复

目标：重启后能恢复任务，并处理工具是否已经执行的不确定性。

进入完整存储实现前先做 SQLite 与故障注入原型：持久化工具执行意图和结果，在“意图已入库、工具结果未知”处强制中断并重启，证明不会自动重做有副作用操作。以原型测得的事务边界、恢复流程和迁移约束重估阶段 3。

### 开发任务

- [ ] S3-01：定义 SessionStore、RunStore 和 ToolExecutionStore，首个实现采用 SQLite，包含 schema 版本和迁移测试。
- [ ] S3-02：保存用户消息、模型响应、工具请求、工具结果和 Run 状态；工具执行前持久化意图，执行后保存结果，关键数据库写入失败时停止推进。
- [ ] S3-03：区分 queued、running、waiting_approval、interrupted、succeeded、failed、cancelled、budget_exhausted；终止原因单独保存，正常空工具回答不等同于业务验收成功。
- [ ] S3-04：工具执行记录包含操作 ID、参数摘要、可重试性和结果；为支持幂等的操作传递幂等键。
- [ ] S3-05：恢复时识别已完成、未执行和结果未知的操作。未知的有副作用操作先核对或要求人工处理，不自动重复执行；不承诺跨外部系统的 exactly-once。
- [ ] S3-06：CLI 支持列出会话、恢复 Run、查看运行记录；校验恢复任务的工作区、权限和配置变化。恢复审批使用持久化记录及原有效期。
- [ ] S3-07：文件修改使用原子替换并记录前后摘要，按需保存差异或检查点；恢复时检测用户新增修改，不盲目覆盖。
- [ ] S3-08：定义历史、执行记录和 Trace 的保留与清理策略，支持导出和备份恢复验证。

主要改动：`internal/context/session.go`、`internal/run`、`internal/tools`、`cmd/claw`；新增 `internal/storage`。

### 验收门槛

- 在模型响应后、工具执行前、工具完成但结果未入库时分别注入进程崩溃，重启后状态可解释。
- 已确认成功的操作不被无条件重做；结果未知的写操作进入核对流程。
- 重启恢复后的 ToolCall/ToolResult 序列合法，不将残缺消息直接发送给 Provider。
- 数据库不可写、迁移失败和配置不匹配均产生明确错误，不悄悄新建空会话继续运行。
- 清空对话不误删已发生的用量记录，恢复后累计预算仍有效。

## 阶段 4：长任务、上下文与调度

目标：任务超过工作记忆窗口后，仍保持目标、约束和执行顺序。

### 开发任务

- [ ] S4-01：上下文分为用户目标与约束、任务状态、决策与证据摘要、近期完整交互和按需资料；保留现有协议配对测试。
- [ ] S4-02：引入模型上下文预算，预留输出空间；压缩后再次校验预算。摘要保留证据引用，摘要失败时采用确定性降级，不能删除核心约束继续执行。
- [ ] S4-03：持久化任务级计划与步骤状态，通过 RunID 关联；Markdown 为可选展示，不再依赖工作区根目录共享 PLAN.md/TODO.md。
- [ ] S4-04：Skills 先加载索引和触发描述，选中后按需加载正文；限制总大小，正确处理元数据解析错误。
- [ ] S4-05：工具声明读写资源和副作用；独立读取并发，相同文件写入互斥，依赖步骤按序运行。任意 Shell 无法可靠推断依赖时保持保守串行。
- [ ] S4-06：子任务具备 ParentRunID、权限子集、局部预算、取消传播和结构化汇报；默认禁止无限递归委派，返回结论与证据位置。
- [ ] S4-07：对暂时性 Provider 故障实施有限退避重试，避免与 SDK 重试叠加放大；参数错误、权限拒绝及有副作用工具错误使用不同恢复策略。

主要改动：`internal/context`、`internal/engine`、`internal/run`、`internal/tools/subagent.go`、`internal/provider`。

### 验收门槛

- 用超过 20 条消息的确定性长任务证明原始目标、禁止事项和已完成步骤仍可恢复。
- 每次模型请求满足预算与消息配对约束；超长系统提示词无法容纳时明确停止或缩减可选内容。
- “写文件 → 编译”保持顺序，并发修改同一文件不丢失更新。
- 父任务取消后子任务退出；子任务不能扩大权限或绕过总预算。
- 401/403 等不可恢复错误不无限重试；限流、超时的重试次数和累计等待均有上限。

## 阶段 5：结果验收、评测与单机发布

目标：能够以证据说明任务是否完成，并发现模型或提示词变更造成的退化。

### 开发任务

- [ ] S5-01：实现 Validator 接口，先覆盖文件存在与内容校验、配置结构校验、Go 构建/测试和命令后置状态校验；校验器使用同一权限与隔离执行层。
- [ ] S5-02：区分“模型结束回答”与“验收通过”，输出已验证、部分完成、失败、无法验证及证据；验收条件来自任务或明确配置，模型不能自行降低标准。
- [ ] S5-03：修订 benchmark，使 MaxTurns、生效预算、Setup/Validate 截止时间和失败成本均被记录；失败用例保留诊断材料。
- [ ] S5-04：建立至少 20 个可复现任务，覆盖工具错误、窗口滑动、写入冲突、预算耗尽、取消、审批、恢复和成功验收。真实模型任务与无网络回归分开运行。
- [ ] S5-05：统一 Run、模型请求、工具与子任务的日志关联；记录错误分类、耗时、重试、终止原因、Token 和费用可信状态，并进行参数及输出脱敏。
- [ ] S5-06：建立 CI：构建、vet、单元测试、相关 race 测试；隔离与崩溃恢复测试使用具备运行条件的独立任务。
- [ ] S5-07：按固定模型、配置和任务集保存质量基线；统计成功率、P50/P95 耗时、每个成功任务成本及人工介入率。发布时保留上一版本及兼容的恢复方案。

主要改动：`internal/eval`、`cmd/bench`、`internal/observability`、`internal/run`；新增 `internal/validation` 和 CI 配置。

### 验收门槛

- 确定性的权限、恢复、取消和预算关键用例全部通过，未关闭的关键缺陷阻止发布。
- 无测试通过证据时，代码修改任务不能报告“已验证成功”。
- Mock 回归不访问真实 API；真实模型评测显式配置费用上限，记录模型与提示词版本。
- 首轮真实评测建立基线后冻结发布阈值：建议成功率下降超过 5 个百分点或成功任务成本上升超过 20% 时阻止自动放行，需结合样本波动分析原因。
- 完成单机候选版本试用，文档说明支持的平台、隔离范围、恢复限制和已知问题。

## 阶段 6：多用户服务与飞书集成

目标：让多用户共享服务时，身份、任务、资源和审批保持隔离。

### 开发任务

- [ ] S6-01：建立用户/租户、会话和工作区绑定；运行请求与查询均校验身份权限，审批检查发起会话和允许审批的人。
- [ ] S6-02：引入有界任务队列、Worker 并发上限、用户配额和背压；同一 Session 排队，事件按 message ID 去重。
- [ ] S6-03：飞书消息使用结构化 JSON 解析；审批接入持久化机制，具备期限、取消、重复处理防护和审计日志。
- [ ] S6-04：服务关闭时停止接收任务、取消或检查点化在途任务，回收进程；重启识别遗留运行状态。
- [ ] S6-05：每个任务使用独立隔离执行环境及受控凭证；限定出口网络和文件保留期，实现资源清理与失效任务回收。
- [ ] S6-06：增加健康检查、队列长度、错误率、预算耗尽率和资源使用监控；告警与运行手册给出明确处理动作。
- [ ] S6-07：在选定硬件上进行 10 个并发会话的初始压测与 24 小时稳定性测试，记录容量上限；按实测确定服务目标，再逐步扩容。
- [ ] S6-08：完成数据备份恢复与版本回滚演练，从少量内部用户逐步开放。

主要改动：`cmd/agentops`、`internal/feishu`、`internal/run`、`internal/storage`、`internal/executor`；按需新增 `internal/scheduler`。

### 验收门槛

- 用户不能查询或操作其他用户的任务、工作区与审批；重复飞书事件不会创建重复 Run。
- 队列饱和时返回明确的排队或拒绝反馈，不无限创建 goroutine。
- 审批超时、重复审批、越权审批与服务重启用例通过。
- 稳定性测试无跨会话消息污染、无持续增长的遗留进程或协程；重启和回滚后的任务状态可核对。
- 服务发布范围只覆盖已验证容量与隔离平台，不将单机测试结果扩展为任意规模承诺。

## 实施与交付规则

- 每个 Sx-xx 任务作为独立、可审查的实现单元，交付代码、针对性测试、配置说明和相关文档更新；涉及跨层行为时做贯穿入口到结果的最小闭环。
- 每个里程碑结束记录实际用时、未通过的验收项和下一阶段估时；任务只有在代码、针对性测试和相应文档均可核验后才勾选。
- 扩展现有 Provider、Registry、Session 和 Reporter 接口，避免为了新增 Run 进行一次性大重构。Run 不保存长期会话历史，也不承包所有业务逻辑。
- 每阶段进入下一阶段前检查验收门槛；发现预算、权限或恢复错误时先修复，不以新增功能替代验收。
- Go 变更运行 `go build ./cmd/... ./internal/...`、`go vet ./cmd/... ./internal/...`、`go test ./internal/...`；并发变更追加相关 race 测试。文档变更检查差异与格式即可。
- 真实 LLM 调用按用户明确授权执行；计划内的模拟、单元和隔离测试无需真实 API。
- 工作区现有 `.claw/`、`.zcode/`、`workspace/` 内容需保留；测试使用独立临时目录，不复用或清空用户工作区。
