# 后续设计：工具能力与副作用元数据

[工具扩展契约](../extending-tools.md) · [调整计划](../learning-quality-plan.md)

状态：应用设计待验证，未实施。当前小型工具示例已经说明，新名称需要跨 scope、Registry 和 engine 核对；真实写工具的统一迁移仍需单独定义。

## 触发条件与候选

当新工具重复需要修改多个名称分类位置，或权限、并发、效果与持久动作的分类出现漂移时，优先比较：

| 候选 | 收益 | 代价与取舍 |
| --- | --- | --- |
| 保留名称规则并补文档与回归 | 兼容成本最低，现有行为清楚 | 工具较少时可继续使用；新增分类仍分散 |
| 增加可选工具描述接口 | 可逐步集中声明只读、变更及范围契约 | 需定义缺省值和冲突检测；仅声明不能授予权限 |
| 强制扩展 BaseTool | 每个工具必须显式声明 | 会影响全部实现和外部适配；没有迁移收益证据前不优先采用 |

## 必须先定的契约

能力描述与执行许可分别设计。至少核对工具可见性、作用范围、是否允许只读并发、是否产生副作用、执行前记录和效果核对方法；未知能力默认保守。当前调用配额、动态身份范围、审批及状态版本仍在 Handler 前检查，不能用静态元数据替换。

名称和元数据冲突应在装配时明确失败；禁止“声明只读”但实际执行写入的自动升级。旧工具行为通过兼容描述保留；旧任务的动作身份、Pending、回执和状态版本不能静默改义。真实远端写工具还需外部幂等身份及结果查询，缺失时不得声称只执行一次。

## 实施前验证要求

使用同一批候选比较现有和候选描述：readonly/子任务不能提权、未知工具保守拒绝、写入执行前可靠登记、版本失效/审批拒绝在副作用前发生、未知效果及存储失败仍阻塞。覆盖现有回执复用与恢复，并运行相关回归及内部 race。新增描述只有减少分类漂移且不改变上述行为时才值得迁移。

[第22讲](https://chatgpt.com/space/page_e0927ee650c881918da61a7a1f66384d)支持工具前沿与执行准入的区分；元数据接口及迁移方式是本项目应用推断，不是课程既定 API，也未由本轮实验验证。
